# CDC 自动接管与备用槽恢复验收

2026-09-21。在前一轮 CDC 基础设施完成后，用户要求先修复固定等待两台备库与旧主槽冲突问题。本次只开发/部署运维保护程序，不开发业务功能。

- S1/S2/S3 各部署常驻 guard 与 Patroni pre_promote 检查，使用现有 etcd 保存有 CAS 保护的候选名单；没有增加服务器或新数据库。
- 普通备库 S2 停止期间，CDC 自动只等待 S3，3.27 秒观察到阶段恢复；S3 同步备库停止期间，自动只等 S2，8.64 秒观察到阶段恢复。两节点恢复后均自动重新纳入。
- S1 的 etcd 出站连接被隔离后，旧主确认只读、S2 自动接管，CDC 只等待 S3；隔离尚未解除时测试事件已收到，观察耗时 40.56 秒。
- 独立新建 failover 探针槽真实复现旧主 S1 回来时 `synced=false` 的同名本地槽。对旧主保持维护隔离，调用已安装程序中的同一自动修复路径，删除的仅是该备库的 inactive/非同步探针槽；主库原槽保留。真实解码和 WAL 推进后，S1/S2/S3 探针槽全部永久、无失效，备库 synced=true。探针最终从主库删除，原生同步清理备用副本。
- 上述槽冲突测试使用一次性探针入口与验证器推进，不冒称活跃 Debezium 槽受到破坏后的完全无人操作演练。实际常驻 guard 已包含相同检测/修复逻辑和恢复标记；没有直接破坏当前服务槽来重复测试。
- 全部 8 个阶段累计 32 条确认事件，32 个唯一 ID 全收，本轮重复 0；不是 exactly-once 承诺。最后恢复 S1 主库、严格同步副本数 1、所有临时 nofailover 标记恢复，故障防火墙链清理。
- 13 项新 guard 安全测试及原脚本 5 项测试通过；覆盖先加屏障后准入、先持久排除后解除等待、CAS 拒绝、无安全副本、位点落后、无效/临时槽拒绝晋升、旧槽删除保护等分支。

这些结果将前一轮两项明确故障从“需要人工处理”推进到“已有自动处理机制和上述场景验证”。仍不是整个系统所有组件的无人值守 HA：双节点故障、磁盘损坏、WAL 超限/槽失效、整机冻结、PG+Kafka 灾备协调和生产安全告警继续保留边界。
